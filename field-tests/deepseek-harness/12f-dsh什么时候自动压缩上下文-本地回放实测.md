# 12f dsh 什么时候自动压缩上下文？压缩前先做了什么？（本地回放实测）

> 测试时间：2026-11-10 00:07–00:30 EST。dsh 0.2.2-rc.1（`--profile headless`，默认配置，模型 `deepseek-flash`，请求里 `max_tokens=256000`），`DEEPSEEK_BASE_URL` 指向本机 127.0.0.1 的 Anthropic Messages 回放服务。**没有真 DeepSeek key，没有调用真实端点**。回报的 token 数是回放服务故意写的，不是真实计数。边界点 n=1。

## 一句话结论
- **实测**：dsh 判断「上下文快满了」用的阈值是 **727,040 token**。它把上一轮模型回报的 `input_tokens + output_tokens` 当基数，再加上之后新增内容的本地估算（字符数 ÷ 4 + 每块 4）。回报 input 724,748 时不触发，724,749 时触发。正好算出 724,749 + 32（output）+ 2,259（新工具结果的估算）= 727,040，一个都不差。
- **实测**：过阈值后，dsh **先做的不是摘要，而是把所有超过 8,192 字符的工具结果剪成「开头 4,096 + `[... tool result middle pruned ...]` + 结尾 1,024」**，连刚跑出来的那一条也剪。模型这一轮就看不到完整输出了，只剩截断提示里的 /tmp 路径（这个路径能不能读回来见 12b（暂未入库））。
- **实测**：真正的摘要压缩要等到「最近约 12.7 万 token 之外还有旧内容可压」才会发生。这次 8,000 字符一步的回放里，第 64 步才出现第一次摘要请求。而且第一次被压掉的是**用户最初那条指令本身**：原文换成模型写的 `<compacted-summary>`，同一步里还会对这份摘要再摘要一次（共 2 次摘要请求）。
- **实测（回放构造的极端情况）**：如果压缩后回报的 token 仍然高于阈值，dsh **每一步固定多发 2 次摘要请求就放弃**，任务继续往下走（4,911 步里每步都是「摘要、摘要、工具」，0 例外）。这和 OpenCode 原地无限压缩不一样（见 [12e](12e-OpenCode什么时候自动压缩上下文-本地回放实测.md)）。不过请求数还是会变成原来的 3 倍。
- **推测**：用真 DeepSeek 时回报值和实际内容一致，要真正装到约 72.7 万 token 才会触发；上面「每步 3 倍请求」只会在网关把 usage 报高时出现。没有用真 key 验证。

## 为什么测这个
[12e](12e-OpenCode什么时候自动压缩上下文-本地回放实测.md) 测出 OpenCode 回报 89.1 万才压缩、压缩后原话不留、usage 偏高会无限压缩。同一个问题放到 dsh 上：几点触发？先丢什么？会不会也死循环？这几件事决定长任务的费用，也决定模型还记不记得你最开始说的话。

## 先读源码猜答案（静态，不是实测）
从本机安装包里 grep 到的常量（原文摘录见 [static-constants.txt](evidence/12f-dsh-compaction/static-constants.txt)）：
- `dsh-compaction-basic`：`thresholdRatio` 0.8、`headroomTokens` 65,536、`retainRatio` 0.16、`compactionRetries` 1；阈值 = `min(上下文窗口 × 0.8, 上下文窗口 − max_tokens − 65,536)`。
- `dsh-llm-deepseek`：官方上下文窗口 1,048,576，默认 `max_tokens` 256,000。
- 代入：min(838,860.8, 1,048,576 − 256,000 − 65,536) = **727,040**。保留尾巴 = ⌊(1,048,576 − 256,000) × 0.16⌋ = 126,812 token。
- `dsh-compaction-tool-result-pruner`：超过 8,192 字符的工具结果剪成头 4,096 + 尾 1,024。
- `dsh-token-meter`：估算按 4 字符 = 1 token，每块加 4；只有回报的 usage 不低于本地估算时才采用回报值。

下面用实测去验证这些推算。

## 怎么测的
1. 新写回放服务 [anthropic_compaction_probe_server.py](evidence/12f-dsh-compaction/anthropic_compaction_probe_server.py)，只监听 127.0.0.1。每一步回一个 `bash` 工具调用（打印 `S<k>` 加 N 个 x），在 `message_start` / `message_delta` 的 `usage.input_tokens` 里写指定的数。如果最后一条用户消息含 `compaction engine`（dsh 摘要指令的开头），就判为摘要请求，回一段固定摘要。可以用 `PT_AFTER` 指定压缩后改报的数。
2. 运行脚本 [run.sh](evidence/12f-dsh-compaction/run.sh)：用法 `R=<项目根> run.sh 标签 端口 步数 每步字符数 回报值[,…] [PT_AFTER]`。需要自己准备 dsh 0.2.2-rc.1，装在 `$R/sandbox/node_modules/.bin/dsh`，回放服务放在 `$R/tools/`。每次用独立 HOME，`--profile headless --json "run the steps"`。
3. 观察的信号有两个：一是请求里工具结果的字符数（9,003 = 原样，5,159 = 被剪）；二是有没有摘要请求。

## 结果

### 1. 小输出（每步 2,000 字符，3 步）：回报 10 万和 80 万都没有变化
- `pt100k`、`pt800k` 都是 5 个请求、0 次摘要，exit 0（[checks.txt](evidence/12f-dsh-compaction/checks.txt)）。
- 解释（**推断**，依据是上面的源码）：80 万已经过阈值，但工具结果没超过 8,192 字符，剪不了；整段对话也比 12.7 万的保留尾巴短，没有可压的范围。所以 dsh 什么都不做，也不报错（headless 下看不到 warn 日志）。

### 2. 大输出（每步 200,000 字符，10 步）：回报值决定模型能看到多少
| 回报 input | 最后一个请求里 10 条工具结果各自的字符数 | 请求体增长 |
|---|---|---|
| 100,000 | 全部 49,931（dsh 自带截断，同 12（暂未入库）） | 每步约 +50KB |
| 800,000 | 全部 5,159（被剪成头 4,096 + 标记 + 尾 1,024，含刚跑完的一条） | 每步约 +5.5KB |

被剪后的样子（x 串已缩写）：`<x*4096>` + `[... tool result middle pruned ...]` + `<x*725>` + 截断提示和 /tmp 路径。剪掉的是中间，**保留了截断提示**。

### 3. 边界：回报 724,748 不剪，724,749 剪
粗扫 70万/72万/72.4万保持原样，72.5万/72.6万/72.7万/73万被剪。之后二分 10 次（[bisect.txt](evidence/12f-dsh-compaction/bisect.txt)）：
- 724,748 → 9,003 字符（原样）
- 724,749 → 5,159 字符（被剪）

核对：724,749 + 32（这一步回报的 output）+ ⌈9,003/4⌉ + 4 + 4 = 727,040，跟源码推算的阈值完全一致。所以**实测确认**：基数是「input + output」，新增内容按字符估算，用的是 `>=`。

### 4. 真正的摘要压缩：第 64 步才第一次出现，先压掉的是用户原话
`real-after`：每步 8,000 字符（剪不到），回报 800,000，压缩后改报 30,000，共 70 步。exit 0，5.18 秒，74 个请求：70 个工具、2 个摘要、1 个标题、1 个最终回答。
- 前 63 步只有正常请求（第 63 步请求体 555,970 字节）。第 64 步之前出现**两次摘要请求**（`max_tokens` 65,536，带全部 24 个工具定义，说明它为了复用缓存，把同样的前缀原样再发一遍）。
- 第 1 次摘要请求只有 1 条消息：用户原话「run the steps」+ 运行时环境说明 + 摘要指令。也就是说，**被压的是最开始那条用户指令**。
- 第 2 次摘要请求的内容是第 1 次生成的 `<compacted-summary>` 加上指令，等于对摘要再摘要。
- 之后的请求里，第一条用户消息变成「自动生成的检查点……」+ 摘要 + `</compacted-summary>`，用户原话不再原样出现。消息条数没少（127 条），请求体反而比上一步大（574,844 字节）。
- 为什么只压这么一点（**推断**）：dsh 固定保留最近约 126,812 token 不动，只压更早的部分；这次回放的真实内容只有约 14 万 token，能压的只有最前面那条。

### 5. 压缩后 usage 还偏高：每步多 2 次摘要，不会原地死循环
`many8k-800k`：同样 8,000 字符一步，但压缩后仍报 800,000，外部 `timeout 400`（[AGGREGATE-many8k-800k.json](evidence/12f-dsh-compaction/AGGREGATE-many8k-800k.json)）：
- 400 秒内 14,797 个请求：工具 4,974 次、摘要 9,822 次、标题 1 次。exit 124（被 timeout 杀）。
- 第 65 个请求起，4,911 组都是严格的「摘要、摘要、工具」，0 例外。工具真的在执行（`run.jsonl` 里有 4,974 个 tool_call 事件）。
- 请求体合计约 3.24GB（工具请求 2.83GB，摘要请求 0.41GB）。
- **注意，这里有回放假象**：我的回放服务按「历史里还看得见几条工具结果」来数步数，而 dsh 每步会把最老的一步压进摘要，所以计数一直停在第 64 步，永远到不了设定的 100 步，最后只能靠 timeout 结束。「一直不结束」是回放造成的，不是 dsh 的行为。dsh 自己的行为是：每步最多压 2 次（`compactionRetries` 1 + 1），压不下去就放弃本步压缩，任务继续。
- 跟 OpenCode 对比：OpenCode 在同样情况下原地反复压缩、任务不推进（12e：20 秒 414 次）；dsh 每步有上限、任务照常推进，但请求数变成 3 倍。

## 这对普通用户意味着什么
- dsh 默认配置下，长任务大约到 **72.7 万 token** 才开始「省上下文」。在这之前每一步都会整份重发（费用问题见 12（暂未入库））。
- 一过阈值，**所有长工具输出都会被剪成头尾**，包括刚跑出来的那一条。如果你依赖模型看完整的日志或测试输出，过了这个点它就只能看到头 4KB、尾 1KB。
- 真正摘要时，最先没的是你最早说的那句需求，之后只剩模型自己写的摘要。长任务里，重要约束最好写进项目文件，或者中途再说一遍，不要只依赖第一条消息。（这是根据观察给的建议，没有做对比实验。）
- 如果中间接了会改写 usage 的网关或代理，要留意请求数是不是突然变成 3 倍。

## 没测的、不能说的
- 没用真 key，不知道真实 DeepSeek 回报的 usage 跟 dsh 本地估算差多少，所以真实场景下几时触发只能按源码和本次推算。
- 摘要内容是回放服务写死的，没测真模型写的摘要质量，也没测会丢掉哪些信息。
- 边界点只测了 `deepseek-flash` 默认配置、n=1；改 `max_tokens` 或 `contextWindow` 后阈值会变（按源码公式推算，没有实测）。
- headless 模式下 dsh 的 warn 日志（比如「step compaction failed」）没有输出到 stderr，所以「压不下去就放弃」是从请求模式和源码推断的，没有直接看到那条日志。
- Claude Code 的压缩触发点还没测。

## 证据
- 目录：[evidence/12f-dsh-compaction/](evidence/12f-dsh-compaction/)。每次运行一个 `run-<标签>/`，里面有每个请求的 meta、`summary.txt`、`run.jsonl`、`server.log`。
- 原始请求体（含 dsh 系统提示、`dsh_session_log` 等）都没有入库。`many8k-800k` 这一组的删除情况如下：
  - **删了什么**：第 121 到 14,797 号原始请求体，共 14,677 个文件，约 3.21GB（3,211,497,923 字节）。整组 14,797 个请求合计约 3.24GB（3,242,233,329 字节）。
  - **为什么删**：体积太大；内容是本地回放服务合成的重复数据；里面还含 dsh 系统提示，不能公开。
  - **留了什么**：第 1 到 120 号原始请求体，合计 30,735,406 字节，和按 body_len 算出来的数一致；完整的文件清单 `many8k-raw-manifest.txt` 有 14,797 行；第 101 号以后的 14,697 个 meta 打包成 `many8k-metas-101plus.tar.gz`。三样都放在 internal-archive/12f-dsh-compaction/，不在公开库里。
  - **怎么核**：文件清单只有文件名，没有大小。上面的字节数是按每个请求 meta 里的 `body_len` 加起来算的，被删的请求体本身已经没有了，没法再量。公开库只有前 100 个 meta 和 [AGGREGATE-many8k-800k.json](evidence/12f-dsh-compaction/AGGREGATE-many8k-800k.json)，所以公开读者能核到的只是汇总数；逐个请求核对要用库外的 meta 包。
- 公开文件里的本机项目路径换成了 `<R>`，见 [MASKING.txt](evidence/12f-dsh-compaction/MASKING.txt)（记录了原件的 sha256）。
- 本轮 dsh 留在宿主 /tmp 的 5 个 spill/subprocess 目录，测完已删除，清单见 `tmp-leftovers-cleaned.txt`。
